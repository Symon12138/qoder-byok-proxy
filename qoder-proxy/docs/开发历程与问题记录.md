## 一、方向：为什么是"代理 + 补丁"这条路

### 目标

Qoder IDE 是闭源的，官方只允许自家和少数白名单 provider 的模型。
目标是：**让 Qoder 使用任意第三方 / 自建 OpenAI 兼容模型**，且不修改 Qoder 的安装包结构。

### 曾经考虑过的方向

| 方向 | 为什么不行 / 可行 |
|---|---|
| 改服务端白名单 | 服务端在 Qoder 手里，改不了 |
| 伪造模型记录里的 provider 字段 | Qoder 会校验；且请求最终仍发往官方后端，官方后端不认这个 provider |
| 反编译重打包 Qoder | 工作量大、每次更新都要重做、签名会失效 |
| **本地 MITM 代理 + bundle 补丁** | ✅ 采用 |

### 最终方案的两条腿

```
① 让 IDE 认这个模型  ← bundle 补丁（改渲染逻辑 + 放行可用性判断）
② 让请求真的发出去  ← MITM 代理（拦截 → 解包 → 改投到你的网关 → 包回 Qoder 格式）
```

**两条腿缺一不可**：

- 只有补丁：IDE 里能看到、能选，但请求仍发往官方后端，官方不认 `custom_model` → 发不出去。
- 只有代理：代理能改投，但 IDE 里根本不显示自定义模型，用户选不到。

这个判断后来被反复验证：清掉补丁只留代理，模型选择器里就没有那一条了。

### 为什么必须 MITM（而不是简单转发）

Qoder 的自定义模型请求并不是直接打你的网关，而是：

```
POST https://api3.qoder.sh/algo/api/v2/service/pro/sse/agent_chat_generation
X-Model-Key: custom_model
body: zstd 压缩 + 自定义 Base64 混淆的 Qoder 请求 JSON
```

也就是说，**请求先发给 Qoder 自己的服务器**，请求体里带着"该用哪个自定义模型"的元信息。
所以必须：

1. 用本地 CA 签发 `api3.qoder.sh` 的证书，让 Qoder 的 TLS 连到我们（`http.proxy` 指向本地）；
2. 解开 zstd + 自定义 Base64，拿到真正的 messages；
3. 自己 POST 到配置的网关；
4. 把上游的 OpenAI 流重新包成 Qoder 的 SSE 信封回传。

### 关键架构判断

| 判断 | 理由 |
|---|---|
| 补丁只改"最小必要点"，不做整段替换 | Qoder 每次更新都会变，改动面越小越容易跟随 |
| 补丁按功能分组开关（`experts` / `repowiki`），不按编号 | 用户关心的是功能，不是 P4 还是 P12 |
| 模型记录写 sqlite，显示相关的东西走补丁 | 记录是数据，渲染是逻辑，混在一起难维护 |
| 不碰 `aicoding.modelConfigs.cache.experts` | 注入条目 schema 不匹配会导致解析失败，且启动被服务端覆盖 |
| 上游只从零构造请求（只带 3 个头），不透传 Qoder 的头 | 避免把 Qoder 的 JWT / cookie 泄漏给第三方网关 |

## 三、问题台账

按"现象 → 根因 → 做法"记录。★ 标记的是**排查特别费劲**或**容易再犯**的。

### A. 模型显示与选择

| # | 现象 | 根因 | 做法 |
|---|---|---|---|
| A1 ★ | 自定义模型出现在「极致」等官方分组里，和官方模型并列 | 补丁 P2/P7/P9 把 custom 模型 `.concat` 进了 `getAvailableModelConfigs` / `queryModelClasses`，而 Qoder 原生已经会把它们渲染进「自定义」分组 → 重复渲染 | 删掉三条注入补丁，只保留原生分组 |
| A2 | 重启 Qoder 后模型选择被重置成默认 | `isModelConfigAvailable()` 只查官方 + 企业列表；登录后 `_handleUserInfoChange` 重新校验并 `setModelConfig(default)`，把用户的 custom 选择覆盖掉 | 新增 P13：在该判断末尾追加 `|| this._isCustomModelExists(e)` |
| A3 | 专家团选不到自定义模型 | 专家团不走普通模型列表，有独立的门控 | P4 解除门控；P5a/b/c 处理标签页与真实模型名显示 |
| A4 | 改模型时显示名不跟着变 | 表单只在初始化时取一次 displayName | 改为模型选中即同步显示名，并给字段加提示「换模型时会自动跟随」 |

### B. 绑定与持久化

| # | 现象 | 根因 | 做法 |
|---|---|---|---|
| B1 ★ | `chat.modelConfig.assistant` **整行消失**（不是被改成 auto，是键都不存在），之后模型选择器不再挂着自定义模型 | Qoder 把模型选择存在内存里，状态变更时整份写回 sqlite；当它此刻认为"选中的模型不存在"（例如刚跑过退出服务、记录被清空），写回时这一项就是空值，行被删掉 | 加**场景绑定守卫**：每 20 秒检查，只在**整行不存在**时补回 `custom:<recordId>`；已有值一律不动 |
| B2 ★ | 误判为"上游失败会清掉绑定" | 定点观测 100 秒（含一次必然失败的对话），三个键原样不动 —— 数据推翻了我的猜测 | 记录在案：失败请求**不会**动绑定；真因见 B1 |
| B3 | 只写模型记录，场景绑定还是旧的 | 早期 `syncRecord()` 只更新记录 | 同步时一并把 `assistant` / `experts` 指向新记录；但**前提是同步成功且记录存在**，否则宁可不动（指向不存在的模型比留在 auto 更糟） |

### C. 配置与端口

| # | 现象 | 根因 | 做法 |
|---|---|---|---|
| C1 ★ | 改了代理端口后，Qoder 静默失联（所有请求不再经过代理，界面无任何提示） | 端口改了但 `settings.json` 里的 `http.proxy` 还是老端口 → 指向一个没人监听的地址 | 保存端口时自动把 `http.proxy` 同步到新端口；手工改配置文件的情况由「IDE 走代理」兜底 |
| C2 ★ | 端口填 `-1` / `99999` 让 `/api/status` **整个接口失败**，控制台所有页面空白 | 非法值一路传到 `portOpen()` 和状态组装 | `proxyPort()` 内部做 1~65535 校验并回退默认；保存端也校验 |
| C3 | 关掉 Qoder 再打开就上不了网 | Qoder 退出时把内存里的 settings 整份写回，可能抹掉 `http.proxy` | 记 `config.ideProxyPort` 作为期望值，守卫每 30 秒核对，丢了就补回（实测 8 秒恢复）。用户主动「退出服务」时标记一起清掉，不打架 |
| C4 | 补丁打到错误目录 / 校验通过但没生效 | `apply-all.ps1` 校验了 `-Root` 却没传给子脚本，子脚本各自用硬编码路径 | 循环里统一传 `-Root`；两个 bundle 都校验存在性；`ABORT` 时 `exit 2` |

### D. 代理数据面（最值钱的一节）

| # | 现象 | 根因 | 做法 |
|---|---|---|---|
| D1 ★★ | 上游连不上 / 返回 500 时，Qoder 界面**只显示用户消息，后面一片空白，既不报错也不结束** | Qoder 不认识代理发回的 SSE `error.code`——在它的两份 bundle 里搜 `upstream_error` / `proxy_error` / `auth_error` / `llm_return_empty`，**全部 0 次出现**；它只认 `rate_limit` / `invalid_request` / `network_error` / `timeout`。而 `envelope()` 又固定写 `statusCodeValue: 200` | 不猜它的错误 UI，直接**合成一条普通 assistant 文本**把错误写进对话（`emitVisibleFailure`），并带处置建议 |
| D2 ★ | 上游返回 200 但内容为空（空流 / 非 JSON / `choices: []`），界面同样静默 | 只统计"有没有写回包"，没统计"写回了多少内容" | 累计 `emittedChars`，结束时为 0 就补可见提示 |
| D3 ★ | 上游吐了半句后正常关闭（没有 `finish_reason`），界面永远停在那半句 | 同上，且没有结束标记判定 | 增加 `sawFinish`，缺失且已有内容时提示"回复在输出中途断开了" |
| D4 ★★ | 中文回复里偶发方块 / 乱码 | `buffer += chunk.toString('utf8')` 逐块解码，一个汉字 3 字节被切在两块之间时，边界会产生替换字符 `U+FFFD` | 换成 `StringDecoder`（跨块保留半截字节）。单元对照：旧写法 3 个替换字符，新写法与原文逐字节相同 |
| D5 ★★ | 上游在一个 SSE data 里吐 8MB，Qoder 能渲染但**持久化失败**：`ENOSPC: no space left on device` / `Disk quota exceeded`，那一轮直接失败（磁盘其实还有 9GB） | 单条消息体量过大触发 Qoder 内部写入限制 | `splitLargeChunk()` 把超过 64KB 的 `delta.content` 切成多片再 envelope（`finish_reason` / `tool_calls` / `role` 挂到正确分片）。修后同样 8MB：正常显示、0 条 ENOSPC |
| D6 | 凭据泄漏风险（设想） | 曾担心把 Qoder 的 JWT 转给第三方网关 | 实测上游只收到 6 个标准头，`authorization` 是我们的 key（13 字符），Qoder 的 JWT / cookie / `x-model-key` 一个都没透传 |

> **D1~D5 的共同教训**：这几条全都表现为"界面看起来没问题"或"界面空白但没有任何报错"。
> 只看界面会误判为成功 —— D5 尤其典型：8MB 全渲染出来了，只有翻 `main.log` 才看到 ENOSPC。

### E. 控制台与数据

| # | 现象 | 根因 | 做法 |
|---|---|---|---|
| E1 ★ | 日志页越用越卡 | `/api/logs` 每次 `readFileSync` 整份文件再切最后 N 行；120MB 时单次 489ms、RSS 涨 191MB，而服务是单线程的 | 只读尾部 2MB（3ms，163 倍）；从中间截断时丢掉半行 |
| E2 ★★ | 模型记录写不进去，且**没有任何报错** —— 改个名字没生效 | SQL 全是字符串拼接没转义，值里一个单引号（`Bob's model`）就让整条 UPDATE 解析失败 | 所有拼进 SQL 的值过 `sqlLit()`（单引号翻倍）。**注意**：修的时候一度没看到 `writeRecords` 里本来就有 `.replace(/'/g,"''")`，加了第二层 → 库里存成 `O''Brien`，用 `hex()` 才查出来 |
| E3 | `bodies/` 与 `proxy.log` 无上限 | 每条对话落 3 个采样文件；日志只增不减 | 磁盘卫生：启动后 20 秒 + 每 30 分钟，bodies 留 400 个、日志超 20MB 滚动（实测 680→400、25.7MB→滚动） |
| E4 | bundle 备份堆了 1.4 GB | 每次应用都留一份 53MB 的 `.bak-experts-*`，从不清 | 每次备份后只保留最近 1 份（实测 26 份 1395MB → 4 份 215MB → 下次应用后 107MB） |
| E5 | 浏览器里任何网页都能调控制台接口 | 绑 127.0.0.1 但无鉴权；带 JSON 的会被 CORS 预检挡下，但 `text/plain` 属"简单请求"不触发预检，而 body 解析只看内容不看头部 | 加 `Origin` 校验：只放行控制台自己，其余 403；命令行不带 Origin 不受影响 |
| E6 | 目录选择框打开时其它操作全部挂起 | 服务端 `spawnSync` 阻塞最长 300 秒，前端 5 秒轮询全部堆在队列里 | 前端 `request()` 按端点设超时（挑目录 320s、同步 120s、其余 20s，超时抛可读错误） |
| E7 | 四份 `esc()` 实现，转义强度还不一致 | 各视图各写一份；`Overview` / `Patches` 的版本不转双引号 | 合并成 `components.js:5` 一份并补上单引号，其余三个视图改为 import |

## 四、验证方法学（这部分比缺陷清单更重要）

### 第一次"全绿"是假的

第二轮回归跑出 76/76，当时以为没问题。后来复核发现至少三类假通过：

| 类型 | 例子 |
|---|---|
| 断言写死 | `rec('日志', '日志行渲染', true, ...)` —— 0 行也标通过 |
| 读了错的东西 | 「重新探测安装目录 → undefined」判 pass，因为只断言 `r.ok` |
| 用重试掩盖 | 「去上游配置」首次点击失败，加了个重试后通过，**首次为何失败从未查清** |

**结论：断言必须给出「期望值 vs 实际值」的可判定比对，不允许硬编码 `true`。**

### 第二轮严格化后

改成每项都输出"期望 / 实际"，去掉所有重试，去掉"基线自愈"，并在每个阶段前校验控制台代码版本：

```
第 1 段 控制台 8 视图交互   45/45
第 2 段 补丁全流程         37/37
第 3 段 Qoder 端到端       28/28
第 4 段 退出服务 + 复原     23/23
```

严格化后立刻抓到两个**上一轮完全没发现**的真缺陷：`apply-all` 没传 `-Root`、
`bindScenesToCustom` 无条件执行。

### 环境一致性

★ **控制台跑的是旧代码**：`apply` 只杀 Qoder 不杀控制台（只有 `revert` 杀），
所以我改完代码再点应用，控制台还是旧进程 —— 一度以为"改了没生效"。
现在测试前会比对控制台进程启动时间与 `admin.js` 修改时间，旧了就重启。

### 推翻自己的结论时，也要重新验证

这一轮我犯过一次"过度更正"：先报告"前端有 5 秒轮询会让请求排队"，被质疑后去查，
用了一次写错的 grep 得到"没有 setInterval"，于是公开更正说"前端根本没有轮询，是我编的"。
后来核对 store.js:349 才确认 \startPolling(5000)\ 一直都在，最初的判断才是对的。

教训：**推翻结论和得出原始结论一样需要证据**。用一次失败的检索去否定前面的观察，
等于把两个错误叠加。凡是要更正已发布的判断，必须同样拿出可复现的依据（文件:行号）。

### 对抗性验证（找"它会不会骗人"）

| 攻击面 | 构造的输入 | 结果 |
|---|---|---|
| 无界数据 | 日志涨到 120MB 再请求 | ❌ 489ms / +191MB RSS → 已修 |

### 第一性原理验证（问"根本假设成立吗"）

不看界面，直接验证前提：

1. **起一个 60 行的假上游**，返回固定标记文本 → Qoder 界面显示 `STUB-UPSTREAM-OK 我收到了你的话：「...探针 token...」`
   → 证明"请求经过代理 → 发到我指定的上游 → 回显"整条链真实成立，且回复确实来自我的服务，不是官方后端。
2. **检查上游收到的全部头部** → 只有 6 个标准头，`authorization` 是我们的 key → 凭据边界干净。
3. **让上游分别返回 500 / 连接拒绝 / 空流 / 半截断流** → 逐一暴露"静默"缺陷。

### 测试脚手架的坑（我自己的 bug，别当产品缺陷）

| 现象 | 真因 |
|---|---|
| 测试脚本永久卡死 | `spawnSync` 启动常驻服务会等子进程退出 → 必须用 `spawn(...).unref()` |
| 每次都误判"控制台是旧进程" | PowerShell 返回本地化日期（`2026年11月1日 0:28:19`），`new Date()` 解析不了 → 用 `.ToString('o')` |
| 点击后什么都没发生 | 无头 Edge 里 `confirm()` 会阻塞页面 → CDP 里自动 `Page.handleJavaScriptDialog{accept:true}` |
| 消息发不出去 | **中文输入法候选条吃掉了第一个回车**（文字停在未上屏状态）→ 连按两次回车 |
| 输入落到别的窗口 | 别的窗口盖住了目标输入框 → 先用 `SetForegroundWindow` 并校验，再点 |
| 空会话找不到输入框 | 空会话输入框在 y≈855，有对话时在 y≈930 |
| PowerShell 脚本报 `Unexpected token '}'` | 5.1 用 ANSI 读文件，中文注释把语法搞坏 → 脚本保持纯 ASCII |
| 测试断言"开关只能关不能开" | 我把字段名写成 `enabled`，后端要的是 `injectTools` |

## 六、如果要重做一次，会怎么做

1. **先确认"请求到底发给谁"**，再决定拦不拦 —— 这一步搞错，后面全是无用功。
2. **补丁改动面尽量小**，只改"最小必要判断"，不做整段替换；每次 Qoder 更新都要能快速定位失效点。
3. **凡是"界面看起来正常"的地方都要去翻日志**（D5 就是这样被发现的）。
4. **测试从第一天就要求"期望 vs 实际"**，不要用重试掩盖首次失败 —— 假的 76/76 比没有测试更危险。
5. **每个后台定时任务都要有"只补缺失、不覆盖已有"的规则**，否则自愈机制会变成和用户抢状态。
6. **写 SQL 一律过转义函数**，哪怕是本地工具。
